# 例行复盘（固定流程）

> 用途：每轮迭代后的固定收尾。用户消息「这是第 N 轮之后的例行复盘」即按本文件执行；
> 历史消息从未附带步骤清单，故以此为准。

## 六步（按顺序，不跳）

1. **归零**
   - `git status --short` 必须干净；有未提交改动先弄清归属（本会话 / 并行会话）再动。
   - `git log --oneline <上次复盘点>..HEAD` 数出区间提交。

2. **全量回归**
   - `bash tools/verify_all.sh`（单测 + lint + 文档生成后的探针）。
   - 任何失败先定位是「产品缺陷」还是「模型波动」：产品缺陷当轮修，波动记入文档并给出预算/重试调整。

3. **区间盘点**
   - 按主题归并（AI / 音频 / 备份 / 工程化 / 构建），不逐条抄 commit。
   - 标注哪些是「用户可感知」的改动，哪些只是内部重构。

4. **沉淀规则**
   - 新出现的坑：先判断能否变成**编译期/测试期约束**（如「AI 回调必填」「去重键契约测试」），能则当轮落地。
   - 不能自动化的，写进项目 `CLAUDE.md`「约定」，并按需同步 Obsidian `inbox/`。

5. **更新计划**
   - `docs/iteration-plan.md` 四栏：已完成 / 可离线队列 / 长尾离线池 / 阻塞。
   - 阻塞项必须写清「等什么」：等真机、等 L1 确认、等外部依赖。
   - 可离线队列为空且阻塞项不可动时，明确写「本轮不新增低价值改动」，不要为凑数加 UI 开关。

6. **归档与汇报**
   - 复盘写 `docs/retro-YYYY-MM-DD.md`（同日多次则追加小节）。
   - Obsidian 追加一条（≤5 行，密度优先）。
   - 给用户三行总结：做了什么 / 怎么验证的 / 下一步。

## 判定口径

- 「已完成」= 有命令输出或测试证据；只有代码没有验证的，写「已实现，待真机」。
- 「阻塞」≠「待办」：阻塞要写明解除条件，避免下一轮重复讨论。
- 真机项一律进 `docs/acceptance-checklist.md` 第八节，不在复盘里等。
